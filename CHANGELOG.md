# История версий

Подробный список изменений по версиям. Если апгрейдитесь с более старой
версии — обязательно посмотрите раздел [DEPLOY.md](./DEPLOY.md#9-обновление-после-изменений-в-коде),
там собраны все накопленные вручную миграции БД по порядку.

## Версия 10 — мелкие доработки

- **Уведомление партнёра при выходе из пары.** Раньше, если один из
  партнёров нажимал «Расформировать пару» посреди игры, второй просто
  оставался в подвисшем состоянии, пока не пробовал что-то сделать сам.
  Теперь сервер сразу шлёт `couple_disbanded` по WebSocket — экран игры
  сам перекидывает на создание новой пары.
- **Список достижений на странице «Аккаунт».** Раньше достижения были
  видны только в момент получения (всплывающее уведомление) — теперь на
  `/account` есть постоянный список уже полученных, плюс базовая
  статистика (монеты, сыграно раундов, лучшая серия совпадений).
- **Жалобы на вопросы в админ-панели.** `report_count` считался и раньше,
  но нигде не показывался — теперь на `/admin` есть отдельный список
  вопросов с жалобами и кнопка «Скрыть вопрос» (мягкая деактивация, как и
  для паков).
- **Rate limiting.** `/auth/login`, `/auth/set-password` и `/admin/claim`
  теперь ограничены по числу попыток с одного IP (простой in-memory
  лимитер — `app/rate_limit.py`, без внешних зависимостей; годится только
  для одного процесса backend, что и так единственный поддерживаемый
  режим — см. "Важное ограничение" в `DEPLOY.md`).

Схема БД не менялась, миграций не требуется.

## Версия 9 — история пар и переподключение

- **Список прошлых пар и переподключение.** Новая таблица
  `couple_memberships` фиксирует, кто и когда состоял в какой паре (в
  отличие от `User.couple_id`, который отражает только текущую пару и
  обнуляется при выходе). Экран `/couples` показывает пары, в которых
  пользователь состоял раньше, с именем партнёра — и кнопку
  «Переподключиться» (`POST /couples/{couple_id}/reconnect`). Работает
  симметрично обычному присоединению по коду: если партнёр ещё не нажал ту
  же кнопку у себя — пара остаётся в режиме ожидания, статус переключается
  на `active` только когда переподключились оба.
- Прогресс (монеты, достижения, история сыгранных раундов) и так никогда не
  удалялся при выходе из пары — это просто первый экран, который даёт им
  видимый и удобный вход назад.

⚠️ История членства ведётся только с этой версии вперёд — пары,
расформированные до деплоя, не появятся в списке (нет данных, чтобы её
восстановить). Подробности и таблица — в `DEPLOY.md`, раздел "Версия 9".

## Версия 8 — приглашение по ссылке и QR-коду

- **QR-код и ссылка-приглашение.** На экране создания пары рядом с
  6-значным кодом теперь показывается QR-код и текстовая ссылка вида
  `/couple?code=123456`. Партнёр может отсканировать QR камерой телефона —
  откроется страница, где вход в приложение (если ещё не заходил) и
  присоединение к паре по коду происходят автоматически, без ручного ввода.
  QR генерируется полностью на клиенте (пакет `qrcode`), без обращения к
  сторонним сервисам — никакие данные приглашения никуда не уходят, кроме
  как в сам QR-код на экране.
- Схема БД и API не менялись — код приглашения тот же самый, ссылка/QR это
  просто другой способ его передать.

## Версия 7 — игровые сессии

- **Игровые сессии вместо одиночных раундов.** Раньше после каждого вопроса
  нужно было заново предлагать пак и ждать, пока партнёр согласится. Теперь
  принятое предложение сразу запускает игровую сессию (`GameSession`) на
  несколько раундов подряд — по умолчанию до 3 вопросов на каждого игрока
  (роль "отвечающего" строго чередуется), фактическое число зависит от
  того, сколько вопросов реально осталось в паке. После каждого раунда —
  как раньше, сразу виден результат; кнопка "Следующий вопрос" отправляет
  `next_round` и переходит к следующему вопросу сессии без повторного
  предложения/подтверждения. После последнего раунда — общий итог
  (`SessionSummary`): сколько совпадений, сколько очков и монет за всю
  сессию.
- Переподключение теперь корректно восстанавливает состояние не только
  внутри активного раунда, но и "между раундами" сессии (например, если
  партнёр обновил страницу сразу после результата, ещё не нажав "дальше") —
  сервер пересобирает последнее сообщение `round_result` вместо того, чтобы
  просто вернуть на пустой экран выбора пака.

⚠️ Добавляет таблицу `game_sessions` и два новых поля у `game_rounds`
(`session_id`, `sequence_number`) — см. раздел "Версия 7" в `DEPLOY.md`
перед деплоем.

## Версия 6 — одновременные ответы

- **Одновременные ответы вместо очереди.** Раньше `answerer` отвечал первым,
  и только после этого `guesser` мог отвечать — сейчас оба получают вопрос
  и могут отвечать сразу, независимо друг от друга (`guesser` в любом
  случае не видит ответ `answerer`'а, пока сам не ответит, так что ждать
  своей очереди не было смысла). Раунд переходит к разрешению, как только
  ответили оба, в любом порядке. Новое сообщение `partner_answered`
  подсказывает игроку, что партнёр уже ответил.
- **Явный баннер роли перед ответом.** Компонент `RoleBanner` теперь
  однозначно показывает, кто есть кто в этом раунде — «🎤 Ваша роль —
  отвечать за себя» или «🔍 Ваша роль — угадывать», вместо мелкой подписи
  под вопросом.

⚠️ У `game_rounds.status` изменился набор значений (`waiting_answer` /
`waiting_guess` → единое `in_progress`) — см. раздел "Версия 6" в
`DEPLOY.md` перед деплоем.

## Версия 5 — обязательное имя и персонализация

- **Обязательное отображаемое имя.** Сразу после первого визита (до перехода
  к паре/игре) приложение просит указать имя — экран `/welcome`
  (`POST /users/me/display-name`). Без имени нельзя ни создать/присоединиться
  к паре, ни предложить раунд. Поменять его позже можно на странице
  `/account`. Это отдельное поле от логина для входа (`username`) —
  имя не уникально и не требует пароля.
- **Персонализация текста вопросов.** В текстах вопросов теперь можно
  использовать `{username}` — при показе он заменяется именем того, кто
  отвечает на вопрос "про себя" (`answerer`), например: `"Что {username}
  ценит в людях больше всего?"` → `"Что Аня ценит в людях больше всего?"`.
  Подстановка происходит на бэкенде (`crud.render_question_text`) прямо
  перед отправкой вопроса по WebSocket — клиент получает уже готовый текст.
  **Важно:** имя вставляется как есть, без склонения по падежам, поэтому
  `{username}` в вопросе должен стоять строго в позиции подлежащего
  (`"{username} любит..."`, `"Что {username} считает..."`), а не как
  дополнение (`"подарок {username}а"`, `"у {username}"`) — иначе для многих
  имён фраза будет грамматически некорректной. Все стартовые вопросы
  (`seed_data.py`) уже переписаны с учётом этого правила — используйте их
  как образец при добавлении своих.

## Версия 4 — логин и пароль

- **Логин/пароль (опционально).** Анонимный вход по-прежнему работает как
  раньше и остаётся способом по умолчанию. Дополнительно на странице
  `/account` можно закрепить за своим (анонимным) аккаунтом логин и пароль
  (`POST /auth/set-password`), а затем входить в него с любого устройства
  через `/login` (`POST /auth/login`), не теряя прогресс.

⚠️ **Схема базы данных изменилась** (у `User` появились поля `username`,
`password_hash`). Если вы уже запускали предыдущую версию, удалите старый
файл БД перед первым запуском новой версии — миграций в проекте нет (кроме
тех, что описаны вручную в `DEPLOY.md`).

## Версия 3 — Docker, админ-панель, паки на модерацию

- **Docker.** Проект полностью контейнеризирован: `backend/Dockerfile`,
  `frontend/Dockerfile` и корневой `docker-compose.yml` поднимают весь стек
  одной командой.
- **Админ-панель (`/admin`).** Отдельного логина/пароля для админа нет —
  права выдаются по секретному ключу (`ADMIN_SECRET_KEY` на бэкенде) через
  `POST /admin/claim`. Из панели можно:
  - загрузить пак вопросов через JSON (сразу публикуется, статус `approved`);
  - посмотреть список всех паков с фильтром по статусу
    (`pending` / `approved` / `rejected`);
  - одобрить или отклонить пак, предложенный пользователем;
  - скрыть (мягко деактивировать) уже опубликованный пак.
- **Пользовательские паки на модерацию.** На экране «Паки» (`/packs`) любой
  пользователь может предложить свой пак вопросов тем же JSON-форматом —
  он уходит со статусом `pending` и появляется в общем списке только после
  одобрения администратором (`POST /packs/submit` → `POST /admin/packs/{id}/approve`).
- **Выбор пака перед игрой + подтверждение партнёра.** Раньше раунд
  запускался сразу по кнопке «Начать раунд» со случайным паком. Теперь один
  партнёр сначала выбирает конкретный пак и предлагает сыграть в него —
  второй должен принять или отклонить предложение, и только после этого
  создаётся раунд (WebSocket-события `round_proposed` / `round_declined`).

⚠️ **Схема базы данных изменилась** (у `QuestionPack` появились поля
`status`, `is_active`, `created_by_id`, `rejection_reason`). Если вы уже
запускали предыдущую версию локально (не через Docker), удалите файл
`backend/couple_questions.db` перед первым запуском новой версии.
