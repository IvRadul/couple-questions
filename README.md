# Вопросы для пары

Веб-приложение для двоих: партнёры по очереди отвечают на вопросы об отношениях,
система сравнивает ответы, начисляет очки, виртуальную валюту и достижения.

## Версия 3 — что нового

- **Docker.** Проект полностью контейнеризирован: `backend/Dockerfile`,
  `frontend/Dockerfile` и корневой `docker-compose.yml` поднимают весь стек
  одной командой. Подробности — в разделе [Запуск через Docker Compose](#запуск-через-docker-compose).
- **Админ-панель (`/admin`).** Отдельного логина/пароля для админа нет —
  права выдаются по секретному ключу (`ADMIN_SECRET_KEY` на бэкенде) через
  `POST /admin/claim`. Из панели можно:
  - загрузить пак вопросов через JSON (сразу публикуется, статус `approved`);
  - посмотреть список всех паков с фильтром по статусу
    (`pending` / `approved` / `rejected`);
  - одобрить или отклонить пак, предложенный пользователем;
  - скрыть (мягко деактивировать) уже опубликованный пак.
- **Пользовательские паки на модерацию.** На экране «Паки» (`/packs`) любой
  пользователь может предложить свой пак вопросов тем же JSON-форматом —
  он уходит со статусом `pending` и появляется в общем списке только после
  одобрения администратором (`POST /packs/submit` → `POST /admin/packs/{id}/approve`).
- **Выбор пака перед игрой + подтверждение партнёра.** Раньше раунд
  запускался сразу по кнопке «Начать раунд» со случайным паком. Теперь один
  партнёр сначала выбирает конкретный пак и предлагает сыграть в него —
  второй должен принять или отклонить предложение, и только после этого
  создаётся раунд (WebSocket-события `round_proposed` / `round_declined`).

⚠️ **Схема базы данных снова изменилась** (у `QuestionPack` появились поля
`status`, `is_active`, `created_by_id`, `rejection_reason`). Если вы уже
запускали предыдущую версию локально (не через Docker), удалите файл
`backend/couple_questions.db` перед первым запуском новой версии.

## Стек

- **Backend:** FastAPI (Python 3.11+), SQLAlchemy, SQLite, WebSocket, JWT
- **Frontend:** Next.js 14 (App Router), TypeScript, Tailwind CSS
- **Инфраструктура:** Docker + docker-compose

## Запуск через Docker Compose

Самый простой способ поднять весь стек — через `docker-compose` из корня
проекта:

```bash
cp .env.example .env
cp backend/.env.example backend/.env
```

Откройте оба `.env`-файла и обязательно смените:
- `backend/.env` → `JWT_SECRET_KEY` и `ADMIN_SECRET_KEY` на случайные строки;
- `.env` (корневой) → `NEXT_PUBLIC_API_URL`, если разворачиваете не на
  `localhost` (см. комментарий в файле — это значение "запекается" в
  JS-бандл на этапе сборки, поменять на лету нельзя).

Затем:

```bash
docker compose up --build
```

- Frontend будет доступен на `http://localhost:3000` (порт настраивается
  через `FRONTEND_PORT` в корневом `.env`).
- Backend/API — на `http://localhost:8000` (`BACKEND_PORT`), Swagger — на
  `http://localhost:8000/docs`.
- SQLite-файл лежит в именованном volume `backend_data`, то есть переживает
  пересборку и перезапуск контейнеров. Для перехода на PostgreSQL достаточно
  переопределить `DATABASE_URL` в `backend/.env`
  (например `postgresql+psycopg2://user:password@db:5432/couple_questions`)
  и добавить `psycopg2-binary` в `backend/requirements.txt` — модели трогать
  не нужно.

Остановить и удалить контейнеры: `docker compose down` (данные в volume
`backend_data` останутся; `docker compose down -v` удалит и их).

## Запуск без Docker (локальная разработка)

### Backend

```bash
cd backend
python3.11 -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env               # смените JWT_SECRET_KEY и ADMIN_SECRET_KEY
rm -f couple_questions.db          # если апгрейдитесь с прошлой версии — см. предупреждение выше

uvicorn app.main:app --reload --port 8000
```

> **Если у вас Python 3.13/3.14:** убедитесь, что установился `sqlalchemy>=2.0.41`
> (`pip show sqlalchemy`). Более старые версии SQLAlchemy падают при импорте на
> новых версиях Python с ошибкой вида `Can't replace canonical symbol for
> '__firstlineno__'` — это несовместимость со свежим CPython, а не проблема
> самого проекта. Docker-образ (`python:3.12-slim`) этой проблемы не имеет.

При старте приложение само создаёт таблицы SQLite (`couple_questions.db`) и
засеивает базу двумя паками вопросов (стартовый бесплатный + платный
«Воспоминания и мечты», оба типа вопросов) и 4 достижениями (`seed_data.py`).

### Frontend

```bash
cd frontend
npm install

cp .env.local.example .env.local   # NEXT_PUBLIC_API_URL=http://localhost:8000

npm run dev
```

Приложение будет доступно на `http://localhost:3000`.

## Как проверить сценарий на два устройства

1. Откройте `http://localhost:3000` в одном браузере (или вкладке инкогнито) — это
   первый партнёр. Приложение автоматически зарегистрирует анонимного
   пользователя и предложит создать пару — нажмите «Создать код приглашения».
2. Откройте `http://localhost:3000` в другом браузере/вкладке инкогнито — второй
   партнёр. Введите полученный 6-значный код в форму «Присоединиться».
3. Оба клиента автоматически попадут на экран игры и подключатся к
   `/ws/{couple_id}` через WebSocket. На экране игры сразу показывается
   список открытых паков (изначально доступен только бесплатный стартовый).
4. Один из партнёров выбирает пак — сервер шлёт предложение
   (`round_proposed`) обоим: у инициатора экран «Ждём ответа...», у второго —
   кнопки «Принять» / «Отклонить».
5. Если партнёр отклоняет — оба возвращаются к выбору пака
   (`round_declined`). Если принимает — сервер случайно выбирает
   невыпадавший вопрос именно из этого пака и назначает роли: `answerer`
   (отвечает "про себя" первым) и `guesser` (угадывает, не видя ответа).
6. `answerer` отвечает на вопрос (текстом или выбором варианта — зависит от
   типа вопроса).
7. Как только он отправлен, `guesser` получает уведомление `your_turn` и
   пытается угадать ответ.
8. Дальше в зависимости от типа вопроса:
   - **Тип `choice`** — совпадение определяется автоматически, оба сразу видят
     результат (`round_result`).
   - **Тип `open`** — `answerer` получает экран ручной проверки
     (`validate_request`) с обоими ответами и нажимает «Совпало» / «Не
     совпало»; после этого результат уходит обоим (`round_result`).
9. Каждый может оценить вопрос от 1 до 5 звёзд или пожаловаться на него.
10. На экране «Паки» (`/packs`) можно открыть дополнительный пак вопросов за
    монеты, а также предложить свой пак на модерацию.
11. Кнопка «Расформировать пару и создать новую» внизу экрана игры вызывает
    `POST /couples/leave` — прогресс пользователя (монеты, достижения)
    сохраняется, можно тут же создать новую пару.

## Админ-панель

1. Откройте `http://localhost:3000/admin`.
2. Введите значение `ADMIN_SECRET_KEY` из `backend/.env` — аккаунт получит
   права администратора (`POST /admin/claim`).
3. На странице можно:
   - вставить JSON пака (или загрузить `.json`-файл) и опубликовать его сразу
     (`POST /admin/packs/upload`, статус сразу `approved`);
   - фильтровать список паков по статусу и одобрять/отклонять предложенные
     пользователями (`POST /admin/packs/{id}/approve` /
     `POST /admin/packs/{id}/reject`);
   - скрывать опубликованные паки (`DELETE /admin/packs/{id}` — мягкое
     удаление, история сыгранных раундов не страдает).

Формат JSON пака (тот же для админской загрузки и пользовательской заявки
на модерацию):

```json
{
  "name": "Название пака",
  "description": "Необязательное описание",
  "price_coins": 30,
  "questions": [
    { "text": "Вопрос со свободным ответом", "category": "быт", "question_type": "open" },
    {
      "text": "Вопрос с вариантами ответа",
      "category": "развлечения",
      "question_type": "choice",
      "options": [{ "text": "Вариант 1" }, { "text": "Вариант 2" }, { "text": "Вариант 3" }]
    }
  ]
}
```

Валидация (`crud.validate_pack_payload`) проверяет: непустое название,
неотрицательную цену, хотя бы один вопрос, непустой текст каждого вопроса,
допустимый `question_type` (`open`/`choice`), а для `choice` — минимум 2
непустых уникальных варианта ответа.

## Аутентификация

В приложении нет логина и пароля. При первом обращении фронтенд вызывает
`POST /auth/register`, backend создаёт анонимного пользователя и выдаёт JWT
(поля `user_id`, `couple_id`, `exp`). Токен сохраняется в `localStorage` и
подставляется в заголовок `Authorization: Bearer <token>` для всех
REST-запросов и как query-параметр `token` при подключении к WebSocket.
После создания/присоединения/выхода из пары токен перевыпускается, чтобы в
нём был актуальный `couple_id`. Права администратора не кодируются в токен —
`is_admin` каждый раз читается из БД, поэтому `POST /admin/claim` не требует
повторного логина.

## Дальнейшие шаги (не входит в каркас)

- Полноценная система пользователей с логином (сейчас это анонимные
  аккаунты + отдельный секрет для админки).
- Предложения раунда (`propose_round` / `respond_round_proposal`)
  сознательно не хранятся в БД — это лёгкий обмен, как и обычные
  уведомления о ходе. Если партнёр в момент предложения не подключён к
  WebSocket, сообщение теряется и нужно предложить пак ещё раз (в отличие от
  самого раунда, чьё состояние переживает переподключение). Если это
  окажется неудобным на практике, стоит завести отдельную таблицу
  `GameInvite` по аналогии с `GameRound` и подтягивать её так же, как
  активный раунд при переподключении.
- История пар: сейчас старая (расформированная) пара просто перестаёт быть
  активной для обоих пользователей, но остаётся в БД со всей своей историей
  раундов. Экрана "мои прошлые пары" пока нет.
- Rate limiting / защита `/admin/claim` от подбора секрета.
